# ClauseWise

**Grounded question answering over the HIPAA regulations, with verifiable citations.**

Ask a compliance question in plain English. Get an answer drawn only from the
regulation text, cited to the section it came from — or an explicit refusal when the
corpus doesn't cover it.

```
Q: How long do I have to notify individuals after a breach?

A: Except as provided in § 164.412, a covered entity must provide the notification
   to individuals "without unreasonable delay and in no case later than 60 calendar
   days after discovery of a breach" (§ 164.404).
```

```
Q: What is the best pizza topping?

A: I don't know — the provided HIPAA documents don't cover this.
   (closest match 0.902 exceeded the 0.75 grounding threshold; the language model
    was never called)
```

---

## The problem

Compliance teams need answers traceable to a specific provision. A general-purpose
chatbot will answer a HIPAA question fluently and confidently whether or not it is
correct, and you cannot tell which you got.

ClauseWise is built so that every claim is checkable. Citations come from **document
structure captured at ingestion** — they are never generated by the language model,
so the model cannot invent one. The UI shows the retrieved excerpts and their
similarity scores, so a reviewer can verify the answer against its sources in
seconds.

## Architecture

```
HIPAA PDF (45 CFR 160, 162, 164)
      │
      ▼
  extraction ──▶ artifact removal ──▶ section-aware chunking ──▶ 498 chunks
      │                                    (+ citation metadata)
      ▼
  embeddings (local, CPU) ──▶ Chroma vector store
      │
      ▼
┌─────────────────────────────────────────────────────┐
│  Query                                              │
│    ├── dense retrieval (semantic)                   │
│    └── BM25 retrieval (terms of art)                │
│              └──▶ reciprocal rank fusion ──▶ top 8  │
│                                                     │
│  Grounding gate: closest distance > 0.75 ──▶ refuse │
│                                    (no LLM call)    │
│                                                     │
│  Otherwise ──▶ Gemini, constrained to excerpts      │
└─────────────────────────────────────────────────────┘
      │
      ▼
  FastAPI (2 replicas on Kubernetes)  ◀── Streamlit UI
      │
      └──▶ /metrics ──▶ Prometheus
```

## Stack

| Layer | Choice | Why |
|---|---|---|
| Embeddings | `all-MiniLM-L6-v2`, local CPU | No API cost or rate limit — embedding runs on every query |
| Vector store | Chroma (embedded) | File-backed, zero infrastructure |
| Sparse retrieval | BM25 (`rank-bm25`) | Legal text is dense with exact terms of art |
| Generation | Gemini (`gemini-3.7-flash`) | Free tier; the only rate-limited component |
| API | FastAPI + Uvicorn | Declarative validation, generated OpenAPI docs |
| UI | Streamlit | Shows retrieval scores, making grounding auditable |
| Container | Docker, `python:3.12-slim` | 703 MB published image |
| Orchestration | Kubernetes (kind, local) | 2 replicas, startup/readiness/liveness probes |
| Monitoring | Prometheus + ServiceMonitor | Custom RAG-quality metrics alongside RED metrics |
| CI/CD | GitHub Actions → GHCR | Tests gate the image publish |

## Design decisions worth explaining

**Section-aware chunking, not fixed-size.** Splitting every N characters produces
chunks that straddle two unrelated provisions. The model then blends half of
§ 164.308 with half of § 164.310 into one fluent, authoritative, wrong answer.
Splitting on section boundaries keeps each chunk self-contained *and* attaches its
citation label for free.

**Citations are structural, not generated.** Each chunk carries its section number
and title as metadata captured during ingestion. The LLM is handed labeled excerpts
and asked to cite them; it never has to determine where text came from, which is
precisely where hallucinated citations originate.

**Hybrid retrieval.** Dense embeddings handle paraphrase ("notify people about a
breach" → "provide notification following discovery of a breach"). BM25 handles
precise terminology — "encryption" appears in only 6 of 498 chunks, where literal
matching outperforms semantics. Reciprocal rank fusion merges the two rankings
without requiring their incompatible score scales to be reconciled.

**Two-layer refusal.** A deterministic distance gate fires *before* the API call, so
off-topic questions cost zero tokens and cannot be prompted around. A prompt
constraint catches the second case: excerpts retrieved within threshold that still
don't answer the question. Both have been observed firing on different failure modes.

**The LLM call is swappable.** `CLAUSEWISE_STUB_LLM=1` replaces generation with a
stub while leaving retrieval fully intact. This is what lets CI run the complete
retrieval path with no API key, and what makes load testing possible against a
rate-limited free tier.

**The vector index is baked into the image, not built at startup.** The index is a
deterministic build artifact, so baking it in gives an immutable image and fast pod
startup — which matters when an autoscaler adds capacity during a traffic spike.

## Measured results

| Metric | Value |
|---|---|
| Indexed chunks | 498 (45 CFR Parts 160, 162, 164) |
| Published image size | 703 MB |
| Test suite | 16 tests, no API key required |
| Citation error rate | 1 chunk / 498 (0.2%) — see Limitations |
| Off-topic refusal | Fires pre-LLM at distance > 0.75 |
| Kubernetes | 2 replicas, self-healing verified under pod deletion |
| Prometheus targets | 2/2 up, 15s scrape interval |

**Image size note:** the default PyTorch wheel bundles CUDA runtime libraries that
are dead weight in a CPU-only container. Installing from the CPU index
(`--index-url https://download.pytorch.org/whl/cpu`) cut the image roughly 70%.

### Custom metrics exposed

Beyond standard request rate, latency, and error metrics:

| Metric | What it tells you |
|---|---|
| `clausewise_refusals_total{layer}` | Which refusal layer is catching queries — infrastructure metrics can't tell you whether answers are good |
| `clausewise_retrieval_distance` | Histogram of closest-chunk distance per query. A rightward shift over time means incoming questions are drifting away from what the corpus covers |
| `clausewise_llm_calls_total` | LLM calls actually made, vs. total requests — the cost-per-query signal |

## Known limitations

Stated deliberately. These were found by measurement, not assumed away.

**Page-spanning section headers are lost.** Where a header falls across a PDF page
boundary, extraction destroys it and the body text is attributed to the preceding
section. Six of 498 chunks are affected; five are *truncated but correctly
attributed*, and one (`164.318-0`) contains Appendix A content while claiming
§ 164.318 — a genuine mislabel. Root cause is in the cleaning stage, which collapses
the document to a single string and discards the line structure needed to
reconstruct split headers. A regression test pins the count at 6 so it can only
decrease.

**Vocabulary mismatch on some queries.** "Encrypt patient data at rest" fails to
retrieve § 164.312, which contains the answer. `all-MiniLM-L6-v2` does not encode
that colloquial phrasing and the statutory term "electronic protected health
information" are the same concept. Confirmed by diagnostic that the target chunk
exists, is correctly labeled, and ranks below 40/498. Three mitigations were
attempted and honestly did not fix this specific query. Deferred to a
domain-adapted embedding model or LLM query expansion.

**No aggregation or summarization.** "What is this document about" retrieves eight
arbitrary chunks and correctly refuses. This is architectural: retrieval selects
passages by similarity to the question, so a question with no specific subject has
nothing to match against. Disclosed in the UI rather than papered over with a
hardcoded summary path.

## Running it

**Requirements:** Python 3.12+, a free [Gemini API key](https://aistudio.google.com/apikey).

```bash
git clone https://github.com/sbitre/ClauseWise.git
cd ClauseWise

python -m venv .venv
source .venv/bin/activate        # Windows: .\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

echo "GEMINI_API_KEY=your_key_here" > .env

python src/embed.py              # build the vector index (~30s)
```

**API:**

```bash
uvicorn src.api:app --port 8000
```

Interactive docs at http://127.0.0.1:8000/docs · metrics at `/metrics`

**UI** (second terminal):

```bash
streamlit run src/ui.py
```

**Docker:**

```bash
docker build -t clausewise:dev .
docker run --rm -p 8000:8000 --env-file .env clausewise:dev
```

**Kubernetes** (local, via [kind](https://kind.sigs.k8s.io/)):

```bash
kind create cluster --name clausewise
kind load docker-image clausewise:dev --name clausewise

kubectl create secret generic clausewise-secrets \
  --from-literal=GEMINI_API_KEY=your_key_here

kubectl apply -f k8s/
kubectl port-forward service/clausewise-api 8000:8000
```

Secrets are injected via `secretKeyRef` — the manifests contain a reference, never a
value, and are safe to commit.

**Monitoring:**

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install monitoring prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace

kubectl apply -f k8s/servicemonitor.yaml
kubectl port-forward -n monitoring svc/monitoring-kube-prometheus-prometheus 9090:9090
```

**Tests** (no API key needed):

```bash
CLAUSEWISE_STUB_LLM=1 pytest -v
```
